# Recipe: typed client from OpenAPI

## When to use

A separate backend (NestJS/FastAPI) publishes `openapi.json`. Types are shared through the contract, not a shared package.

## Verify first

`/context7` → `openapi-typescript`, `openapi-fetch` (current CLI flags and client API).

## Packages

`openapi-fetch` · dev: `openapi-typescript`

## Files

- `src/lib/api/schema.d.ts`: generated by `pnpm api:types` (`openapi-typescript <url-or-file> -o src/lib/api/schema.d.ts`). Committed.
- `src/lib/api/backend.ts`: `createClient<paths>({ baseUrl: clientEnv.NEXT_PUBLIC_API_URL })`; middleware converting non-2xx into `ApiError` so the rest of the app keeps one error model.
- Feature hooks call `backend.GET('/items/{id}', { params })` inside TanStack Query.
- Script `"api:types"` in `package.json`.

## Env vars

`NEXT_PUBLIC_API_URL` = backend origin (already in the schema).

## Rules to append to AGENTS.md

- Never hand-edit `schema.d.ts`; regenerate after backend contract changes.
- CI fails if the committed types drift from the backend's published spec (`pnpm api:types && git diff --exit-code`), when the spec is reachable from CI.

## Tests to add

Feature hook tests with `fetch` stubs matching the contract; one contract smoke test that the generated types compile against a sample response.

## Pitfalls

- Tokens: use httpOnly cookies set by the backend or a BFF route handler; never put access tokens in `localStorage` or Zustand persist.
- CORS: prefer same-origin via a reverse proxy path (`/api`) over wide CORS on the backend.
